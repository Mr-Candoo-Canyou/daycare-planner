# Iqaluit Daycare Network (IDN)

Centralized daycare enrollment & waitlist platform for Iqaluit, Nunavut — one free application, ranked-choice waitlists across every participating daycare, full transparency for parents, full autonomy for providers.

Built to **[SPEC.md](./SPEC.md)** (v2.1). This repository contains the complete v1 scope: directory, unified application, the ranked-choice waitlist engine, offers with holding fees, daycare waitlist management with priority-rule templates, the funder dashboard, and the IT administration panel. Operations modules (attendance, staff scheduling, subsidy tracking) are v2 per SPEC §7.7.

## Quick start

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # waitlist engine unit tests (vitest)
npm run test:db    # Supabase migrations + RLS tests (in-process Postgres)
npm run build      # type-check + production build
```

The app runs in **demo mode**: a local data adapter seeds realistic sample data into `localStorage`, and sign-in is a one-click account picker. Use the *Reset demo data* link in the banner to start fresh.

## Architecture

```
src/
  domain/
    types.ts        Data entities (SPEC §6)
    waitlist.ts     Ranked-choice engine — pure, unit-tested (§4.2.2–4.2.7, §4.3)
    seed.ts         Demo data
    store.ts        Local repository adapter (localStorage + useSyncExternalStore)
  auth.ts           Session + role grants + role-context switching (§7.5)
  i18n/             i18next; en.json generated by `npm run i18n:extract`
  pages/            One folder per role: parent/, daycare/, funder/, it/
supabase/
  migrations/       Production schema, RLS policies, business-logic RPCs (§7.3)
  functions/        Edge Functions: notify (Twilio/FCM/email), expire-offers
  tests/            21 tests: migrations + RLS + cascade against real Postgres
docs/
  DEPLOYMENT.md     Hetzner + self-hosted Supabase runbook (§7.1–7.4, §7.8)
  BACKEND.md        Domain-function → RPC mapping and adapter swap plan
```

The production database layer is complete and tested: the same waitlist
rules the frontend engine implements live in SECURITY DEFINER functions
(`00002_functions.sql`), role scoping from SPEC §3 is enforced by RLS
(`00003_rls.sql`), and `npm run test:db` proves both against an in-process
PostgreSQL 18 — parents can't read each other's children, daycares never
see rankings, funders never see child rows, the audit log is append-only.

Two deliberate seams keep the demo honest with the production design in SPEC §7:

- **Repository interface** — all reads/writes go through `store.ts` + pure functions in `waitlist.ts`. The production build swaps the local adapter for the Supabase client (PostgreSQL + RLS); the cascade/holding-fee/offer rules move into Edge Functions unchanged, because they never touch the storage layer.
- **Notification dispatch** — `notify()` records an SMS → push → email attempt per user (§4.2.3). Production wires the same call to Twilio and FCM from an Edge Function.

Everything user-facing goes through `t('key', '…default…')`; `npm run i18n:extract` regenerates `src/i18n/en.json` from source. Adding Inuktitut later = adding `iu.json`.

The app is an installable PWA (manifest + app-shell service worker). Offline queueing of writes and stale-data indicators per §7.3 are wired for the attendance module in v2.

## What's real vs. simulated in this build

| Real | Simulated |
|---|---|
| Full waitlist engine: tiers, cascade on acceptance, holding fees, concurrent offers, withdrawal, age-group derivation | Authentication (demo account picker instead of Supabase Auth) |
| Role scoping in every view (data minimization per §5) | SMS/push/email delivery (recorded per channel, not sent) |
| Audit log, small-cell suppression, consent-gated outreach flag | Payments (holding fee marked paid on accept) |
| Configurable application form (versioned schema, no-code editor) | Server-side offer expiry (swept on app load instead of cron) |

## Tests

`npm test` runs 20 unit tests over the engine — tier ordering, manual reordering boundaries, offer expiry, the acceptance cascade (rank-1 vs. lower-rank, retained lists, superseded offers, seamless transition), withdrawal, holding-fee lapse, and funder aggregation. A Playwright smoke script exercising all 13 user flows end-to-end lives outside the repo and was run against the production build.
